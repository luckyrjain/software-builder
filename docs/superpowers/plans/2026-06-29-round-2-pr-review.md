### Task 2: AI-generated code review guidance (P1-10)

**Files:**
- Modify: `pr-review/workflow/phase-2.md`

**Context:** §15 covers LLM usage patterns in code (when the service *calls* an LLM). There is no guidance for reviewing *AI-generated implementations* (Copilot, Claude, GPT). AI-generated code has distinct failure modes — hallucinated APIs, confident-but-wrong logic, inconsistent internal references — that require different detector emphasis than human-written code.

- [ ] **Step 1: Verify gap**

  Read `pr-review/workflow/phase-2.md`. In the `## Conditional dimensions` section, confirm there is no §18 for AI-generated code.

- [ ] **Step 2: Add §18 to the conditional dimensions section**

  In `pr-review/workflow/phase-2.md`, in the `## Conditional dimensions` section, after the `**§8 Test quality**` line, add:

  ```markdown
  **§18 AI-generated code** — when the diff contains markers or comments indicating AI-generated implementation (`// Generated by`, `# AI-generated`, `// Copilot suggestion`, `# Claude`, `Co-Authored-By: github-copilot`), or when the MR description or author notes that AI tools were used to write the implementation:

  Focus detectors on AI-generation failure modes — these differ from human-written bugs:

  | Failure mode | What to look for |
  |---|---|
  | **Hallucinated APIs** | Method calls on types that don't exist in the diff or repo, non-existent library functions, invented config keys |
  | **Confident-but-wrong logic** | Plausible-looking but incorrect algorithms — off-by-one, wrong comparator, silently wrong edge case. Requires tracing the logic, not just pattern-matching. |
  | **Inconsistent internal references** | Variable names, function names, or IDs defined one way in one part of the diff and referenced differently elsewhere in the same diff |
  | **Missing error propagation** | AI scaffolds happy-path code; check that error returns from called functions are handled |
  | **Stale imports / unused deps** | AI often scaffolds more imports than the generated code needs |

  Apply §18 regardless of fast path when triggered — AI-generated implementations warrant extra correctness scrutiny. Prefix findings `ai ·`. Do not suppress §18 findings via stop-search thresholds — complete the §18 pass before stopping.
  ```

- [ ] **Step 3: Commit**

  ```bash
  git add pr-review/workflow/phase-2.md
  git commit -m "feat(pr-review): add §18 AI-generated code review dimension to Phase 2 (P1-10)"
  ```

### Task 3: Multiple Jira tickets with conflicting ACs (P2-10)

**Files:**
- Modify: `pr-review/workflow/phase-1.md`

**Context:** Phase 1 step 6 says "If multiple keys found, load all and merge their acceptance criteria" but gives no guidance when those ACs conflict. An MR linked to two tickets where one says "response < 200ms" and another says "response < 500ms" results in ambiguous review output.

- [ ] **Step 1: Verify gap**

  Read `pr-review/workflow/phase-1.md` step 6. Find the "If **multiple keys found**" sentence. Confirm it ends with "note which ticket each AC came from" — no conflict guidance.

- [ ] **Step 2: Extend the multiple-keys sentence with conflict handling**

  Find this text in step 6:

  ```
  If **multiple keys found**, load all and merge their acceptance criteria (note which ticket each AC came from).
  ```

  Replace with:

  ```
  If **multiple keys found**, load all and merge ACs into the checklist table (prefix each criterion with `[KEY-NNN]` to identify its source ticket). When ACs **conflict** (e.g. KEY-A requires response < 200ms, KEY-B requires response < 500ms), flag the conflict explicitly:

  > ⚠️ **Conflicting AC** — KEY-A: response < 200ms vs KEY-B: response < 500ms. Clarify with the author which requirement applies before merge.

  Emit the conflict as a **Medium** finding. In the AC checklist, use the **stricter** requirement as the default evaluation criterion unless the MR description or author comments explicitly resolve the conflict. Never silently pick one ticket's AC over another — always surface the conflict.
  ```

- [ ] **Step 3: Commit**

  ```bash
  git add pr-review/workflow/phase-1.md
  git commit -m "feat(pr-review): add conflicting-AC detection and resolution guidance to Phase 1 step 6 (P2-10)"
  ```
