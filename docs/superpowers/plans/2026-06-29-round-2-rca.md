### Task 1: Multi-hop cascade analysis (P1-4)

**Files:**
- Modify: `incident-rca/reference/evidence-schema.md`

**Context:** `dependency_failure` is listed as a hypothesis type, but the schema gives no investigation steps for tracing A→B→C failure chains. Agents rely entirely on reading error messages and guessing when this hypothesis wins.

- [ ] **Step 1: Verify gap**

  Read `incident-rca/reference/evidence-schema.md`. In the `## Hypothesis types` table, confirm `dependency_failure` has no dedicated investigation steps section.

- [ ] **Step 2: Add cascade investigation section**

  After the `## Hypothesis types` table, add a new section:

  ```markdown
  ## `dependency_failure` — cascade investigation steps

  When `dependency_failure` is a top-scoring hypothesis, trace the cascade before writing the final report:

  1. **Identify the error path** — scan `error_signals[].sample_messages` for upstream service names, gRPC status codes, circuit breaker messages, or timeout patterns that point to a downstream call.
  2. **Pivot to the downstream service** — re-run Phase 1 queries (`analyze_datadog_logs` or `analyze-logs`) scoped to `service:<downstream>` in the same window. If the downstream also has error spikes, it is a cascade candidate.
  3. **Iterate until the chain terminates** — repeat step 2 on each new downstream until either:
     - A service has errors but its downstream does not → **root service found**
     - The chain exceeds **3 hops** → note *"Deep cascade — recommend distributed tracing for full chain"* and stop manual pivoting.
  4. **Use traces when available (preferred)** — `search_datadog_spans` or `analyze-traces` scoped to the upstream service can reveal the actual call chain directly, without manual pivoting. Use when Datadog APM or KubeSense traces are available.
  5. **Report the chain** — list hops in order: `A → B → C (root)`. State primary hypothesis `dependency_failure`; identify root service as `C`. Note each hop's error rate and approximate timing.

  **Confidence cap:** if the root service (C) is outside your Datadog/KubeSense scope (third-party, different org), cap confidence at **MEDIUM**.
  ```

- [ ] **Step 3: Commit**

  ```bash
  git add incident-rca/reference/evidence-schema.md
  git commit -m "feat(rca): add multi-hop cascade investigation steps for dependency_failure (P1-4)"
  ```

### Task 3: Runbook lookup (P1-7)

**Files:**
- Modify: `incident-rca/workflow/phase-1.md`

**Context:** Phase 1 symptom detection collects error signals and ends with a checkpoint. There is no step to check whether an existing runbook covers the emerging hypothesis. Known playbooks go unsurfaced during investigation, and Phase 5 always adds "Create runbook" to actions even when one already exists.

- [ ] **Step 1: Verify gap**

  Read `incident-rca/workflow/phase-1.md`. Confirm there is no runbook lookup step before or after the `## Phase 1 checkpoint`.

- [ ] **Step 2: Add runbook lookup section**

  After the `## Phase 1 checkpoint` section (after the "User says stop" line), add:

  ```markdown
  ## Runbook lookup (optional — when a hypothesis type is emerging)

  After collecting `error_signals`, if a probable hypothesis type is forming (e.g. consistent OOM signals suggest `infra_capacity`), check for an existing runbook before proceeding to Phase 2:

  1. **Search known locations** (in order):
     - User-provided runbook path or URL
     - `RUNBOOKS.md` or `runbooks/` directory in the repo root (git MCP)
     - Confluence space (if MCP connected and user has confirmed the Confluence space key)
  2. **Match by symptom keywords** — search for the service name, hypothesis keyword (e.g. `OOM`, `consumer lag`, `deploy regression`), or symptom phrase.
  3. **If found** — record runbook URL/path in `evidence_links[]` with `signal_type: "runbook_match"`; surface in Phase 5 Post-RCA actions table as *"Existing runbook found — link in evidence."*
  4. **If not found** — note `runbook_match: none` in Gaps; Phase 5 Post-RCA actions will include *"Create runbook for this failure type."*

  **Non-blocking:** do not delay Phase 2 for runbook lookup. Run in parallel or skip if tool latency is high.
  ```

### Task 6: Multi-site Datadog (P2-7)

**Files:**
- Modify: `incident-rca/workflow/phase-0.md`

**Context:** Phase 0 detects a single Datadog instance. Some organisations run multiple Datadog sites (US1, EU, US3) with separate API keys. Incidents that span sites return zero data on one site while evidence exists on another, and there is no guidance for handling this case.

- [ ] **Step 1: Verify gap**

  Read `incident-rca/workflow/phase-0.md`. Confirm there is no multi-site Datadog detection guidance.

- [ ] **Step 2: Add multi-site section**

  After the "Quick check — existing incident record" section at the end of `incident-rca/workflow/phase-0.md`, add:

  ```markdown
  ## Multi-site Datadog

  Some organisations run **multiple Datadog instances** (US1 `datadoghq.com`, EU `datadoghq.eu`, US3 `us3.datadoghq.com`, US5 `us5.datadoghq.com`, AP1 `ap1.datadoghq.com`). Incidents that span sites require querying each site independently.

  **Detection:** apply this section when any of the following is true:
  - `ddconfig` or user reports multiple Datadog sites.
  - Querying the configured site returns zero metrics/logs for a service the user confirms exists.
  - Phase 1 returns an unexpectedly empty `error_signals` array.

  **Steps:**
  1. Ask the user which Datadog site(s) the affected service reports to.
  2. For each site: set the appropriate `datadog_site` in ddconfig before querying.
  3. Collect `error_signals` and `infra_signals` from each site independently.
  4. Label evidence by site: `"source": "datadog_eu"`, `"source": "datadog_us1"`, etc.
  5. Record which site each query ran against in `query_references[]`.
  6. **Confidence cap:** evidence requiring correlation of signals from **two different sites** is capped at **MEDIUM** — cross-site clock drift can reach ~1 minute.

  If only one Datadog site is configured, skip this section.
  ```
