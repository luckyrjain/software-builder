# `sb` CLI — Read-Only Diagnostics Slice — Design

**Status:** Approved (user-approved in brainstorming dialogue 2026-09-12)
**Date:** 2026-09-12
**Type:** Architectural (new distribution surface)
**Target:** `luckyrjain/software-builder`
**Spec path:** `docs/superpowers/specs/2026-09-12-sb-cli-diagnostics-design.md`

## Goal

Ship a genuinely installable `sb` command (`pipx install software-builder-cli`) that can run
`doctor`, `list`, `explain`, and `compatibility` against an **installed skill with no
software-builder checkout present** — closing the audit gap that "validation/compatibility tooling
only exists inside the repository checkout, not in installed skill packages"
(`docs/skill-framework/shared/runtime-contract.md:168-176`).

This is a deliberately narrowed first slice of the audit's Phase 4 ("a real `sb` CLI"). `sb
install`/`uninstall`/`verify` (a Python port of `install.sh`'s locking/ownership-hardening/rollback
logic) and `sb update --channel` (no release-channel concept exists anywhere yet) are explicitly
**out of scope** — each needs its own brainstorm and spec once this packaging/bundling skeleton
exists and is proven.

## Why this is safe to build now, and why it needs its own package

`pyproject.toml` at the repo root states, deliberately: *"no build backend: the toolchain is run
from a checkout, not installed."* That decision stands and is not reversed by this spec — `sb` is
not "package up `scripts/`"; it is a **separate, independently-versioned package** that vendors a
release-time snapshot of `scripts/`'s logic and the canonical registry data, the same way an
installed skill vendors a snapshot of its own `SKILL.md` rather than depending on the live
checkout.

This works with almost no new business logic because every function `sb` needs already takes an
explicit root parameter — `scripts/doctor.py`'s `main()` already accepts `--repo-root` (defaulting
to the checkout root only via argparse's `default=ROOT`), and `scripts/registry/cli.py`'s commands
already thread a `root: Path` through. `sb` calls these same functions as a library import, always
passing `repo_root=<sb's bundled snapshot dir>` instead of a checkout path. Zero fork of resolution
logic — only packaging, bundling, and one new subcommand.

## Architecture

```
release cut (VERSION bump)
        │
        ▼
scripts/build_sb_snapshot.py (new, standalone — see below)
        │
        ├─► copies scripts/doctor.py, scripts/registry/*.py (unmodified)
        │     into cli/sb/_vendored/scripts/...
        │
        └─► copies skills.yaml, agent-hosts.yaml, scripts/registry/*.yaml,
              skills/** (every skill's real SKILL.md/reference/ files —
              validate_canonical_manifest checks these exist), and
              docs/skill-framework/** (unmodified, git-tracked only)
              into cli/sb/_registry_snapshot/... (~11M total)
        │
        ▼
cli/ (own pyproject.toml, own build backend e.g. hatchling)
        │
        ▼
python -m build  →  software-builder-cli-<VERSION>-py3-none-any.whl
        │
        ▼
pipx install software-builder-cli  →  `sb` on PATH
        │
        ▼
sb doctor / sb list / sb explain / sb compatibility
   (call vendored scripts.doctor.cmd_doctor(repo_root=<snapshot dir>, ...) etc.)
```

**Package layout (new, this spec):**

```
cli/
  pyproject.toml              # name="software-builder-cli", build-backend=hatchling
  sb/
    __init__.py
    __main__.py                # argparse entry point, console_script "sb"
    _paths.py                  # locates the bundled snapshot dir at runtime (importlib.resources)
    _vendored/                 # build-time copy target — populated by scripts/build_sb_snapshot.py, gitignored
    _registry_snapshot/        # build-time copy target — populated by scripts/build_sb_snapshot.py, gitignored
  tests/
    test_sb_doctor_parity.py
    test_sb_list_parity.py
    test_sb_explain_parity.py
    test_sb_compatibility.py
```

`cli/sb/_vendored/` and `cli/sb/_registry_snapshot/` are build-time-populated and **not** checked
into git (same treatment as `generated/` for build artifacts that must always match their source —
except these are *inputs* to a build, not build outputs, so they're regenerated by
`scripts/build_sb_snapshot.py` before `python -m build`, never committed empty-vs-populated
ambiguity).

**Why a new script instead of extending `scripts/package_release.py`:** that script builds a wholly
different artifact (a checksummed, git-tracked-files-only tarball of the *skill distribution*,
with its own `_is_release_excluded` filter that deliberately excludes `scripts/` dev tooling from
that bundle). Wedging cli-snapshot logic into it would fight that exclusion design and entangle two
unrelated release artifacts in one already-517-line, integrity-sensitive file. `sb`'s snapshot step
is a small, standalone script instead — same versioning source
(`scripts/release_info.read_distribution_version`), otherwise independent.

**Version identity:** `cli/pyproject.toml`'s `[project].version` is read from the same root
`VERSION` file at build time (same mechanism `scripts/release_info.read_distribution_version`
already provides) — never hand-set, never allowed to drift, the exact failure mode Phase 0's
plugin-version-sync validator (`scripts/check_plugin_version_sync.py`) already exists to catch for
`.codex-plugin/plugin.json`. That validator's `PLUGIN_MANIFESTS` tuple gains `cli/pyproject.toml`
as a new entry (its `version =` line, not JSON — the validator needs a second, TOML-shaped read
path; see Task breakdown).

## Commands (this slice)

- `sb doctor [--skill ID] [--agent HOST] [--surface KIND] [--install-root PATH ...]` — same
  output shape as `python3 -m scripts.doctor`, but `--install-root` defaults to **every user-scope
  target the resolved host's own surfaces declare**, not just `~/.cursor/skills`. Concretely: after
  `resolve_host(host_registry, args.agent)` resolves a `HostSpec`, default `install_roots` to
  `resolve_target_path(binding.target, home=Path.home(), target_dir=None)` for every
  `binding in surface.discovery` across `host.surfaces`, filtered to `binding.target.scope ==
  "user"` (a project-scope target needs a `--target-dir` doctor has no context for outside a
  specific project, so those are left for an explicit `--install-root`, matching today's
  behavior). This reads directly off `agent-hosts.yaml`'s already-resolved discovery bindings — not
  `scripts/registry/install_resolver.py`, whose `SELECTORS` vocabulary (`"cursor-project"`,
  `"claude-user"`, `"all"`, ...) is install.sh's own destination-selector strings, a different and
  finer-grained vocabulary than the host ids/aliases `doctor --agent` actually takes (`"claude"`,
  `"cursor"`) — passing `args.agent` straight into `install_resolver.resolve_install_destinations`
  would raise `unknown --agent 'claude'` for exactly the host ids doctor already resolves. This
  same default-scan fix lands in `scripts/doctor.py` itself first (shared code, checkout users
  benefit too), and `sb` inherits it for free via vendoring.
- `sb list` — identical to `python3 -m scripts.registry list`.
- `sb explain <skill-id>` — identical to `python3 -m scripts.registry explain <skill-id>`.
- `sb compatibility --host HOST [--skill ID]` — **new** subcommand, added to
  `scripts/registry/cli.py` itself (shared code, not sb-only), wrapping
  `compatibility_resolver.resolve`/`resolve_matrix`. Prints one line per (host, skill) result (or a
  single result when `--skill` narrows it), reusing `CompatibilityResult`'s existing fields
  (`status`, `missing_required`, `missing_optional`, `discoverable`). No new resolution logic —
  this command's only job is CLI plumbing around what already exists.

  **No `--surface` flag in this slice.** `main`'s `compatibility_resolver.resolve()` does not yet
  accept a `surface_kind` parameter as of this writing — that lands in the still-open PR #256
  (Phase 1, "per-surface capabilities"). Adding a `--surface` flag with no backing implementation
  now would be dead scaffolding. This branch is built against `main` as-is (confirmed with the
  user) so it stays independently mergeable rather than stacking on an unmerged PR; `--surface`
  support for both `sb compatibility` and `sb doctor` becomes a small, separate fast-follow once
  #256 merges (see Explicitly Deferred).

All four commands are read-only: no flag in this slice writes to disk, installs, uninstalls, or
mutates a manifest.

## Data flow for a single command (e.g. `sb doctor --skill security-review --agent claude`)

1. `sb/__main__.py` parses argv, resolves `_paths.snapshot_root()` (the installed package's bundled
   `_registry_snapshot/` directory via `importlib.resources.files("sb") / "_registry_snapshot"`).
2. Calls `scripts.doctor.cmd_doctor(repo_root=snapshot_root, skill_filter="security-review", ...)`
   — the exact same function `python3 -m scripts.doctor --repo-root <checkout>` calls, just pointed
   at the bundled snapshot instead of a live checkout.
3. `cmd_doctor` internally still does everything it does today: parses the snapshot's
   `skills.yaml`/`agent-hosts.yaml`, resolves capabilities, checks the *installed* skill's actual
   presence/version via each install target's `.software-builder-manifest.json` (this part already
   reads from wherever `--install-root` points, i.e. the user's real machine — never the snapshot),
   and renders the same status lines.
4. Exit code and output are byte-for-byte what a checkout invocation would produce for the same
   registry version — proven by the parity tests below.

## Testing

**Parity tests** (`cli/tests/test_sb_*_parity.py`): for each of `doctor`/`list`/`explain`, build a
tiny fixture registry (reusing `scripts/tests/`' existing fixture-building helpers where they
already exist), run the *checkout* function once with `repo_root=<fixture>` and once via `sb`'s
vendored copy with the same fixture copied into a temp `_registry_snapshot/`-shaped directory,
assert identical stdout/exit code. This is the test that would catch vendoring drift (e.g. someone
hand-edits the vendored copy instead of re-running the snapshot step).

**`sb compatibility` tests**: since this is new logic (not vendored), test it directly against
`compatibility_resolver.resolve_matrix`'s existing test fixtures in
`scripts/tests/test_compatibility_resolver.py` — same fixture-building conventions, no new pattern.

**Vendoring is git-tracked-files-based, not a hand-maintained allowlist, and it's bigger than YAML
alone.** Empirically verified (not assumed) by running `cmd_list` against a directory containing
only `skills.yaml`/`agent-hosts.yaml`/`scripts/registry/*.yaml`: it fails per-skill with `missing
entrypoint .../skills/<id>/SKILL.md` — `cmd_list`/`cmd_explain` go through
`validate_canonical_manifest`, which checks each skill's actual `entrypoint` file exists on disk.
So the snapshot must include the full `skills/` tree (every skill's real `SKILL.md` + `reference/`
files), plus `docs/skill-framework/` (the P1 contract docs `scripts/registry/layers.py` checks for:
`runtime-contract.md`, `host-adapter-contract.md`, `eval-contract.md`). Measured total: `skills/`
7.3M + `docs/` 2.2M + `scripts/` (minus `tests/`) 1.8M ≈ 11M — trivial for a pip package, not a
reason to special-case or bypass the validation instead.

`scripts/build_sb_snapshot.py` therefore uses `git ls-files` (its own minimal invocation, not
`scripts/package_release.py`'s private `_tracked_files` — that function is a release-tarball
implementation detail returning tar-specific metadata, not a general "list files" API, and
leading-underscore names are this codebase's own convention for module-private) scoped to
`skills/`, `docs/skill-framework/`, `scripts/` (minus `tests/`), and the root `skills.yaml`/
`agent-hosts.yaml`/`VERSION` files (`VERSION` is required too — `cmd_doctor` calls
`read_distribution_version(root)` — confirmed by running all four target code paths, `cmd_list`,
`cmd_explain`, `cmd_doctor`, and `compatibility_resolver.resolve`, end-to-end against exactly this
file set), copying each into the matching relative path under
`cli/sb/_registry_snapshot/` (data) or `cli/sb/_vendored/` (code, `scripts/` only). Git-tracked
only — same reasoning as `package_release.py`: untracked local cruft can never leak into what
ships. A glob/git-ls-files-driven copy, not a curated list, so a new registry YAML, a new
`scripts/registry/*.py` module, or a new skill is included automatically with zero maintenance.

**Build-step test**: rather than diffing a copy list against imports (which a glob makes
unnecessary), the test is a real functional smoke check: run the snapshot step into a temp
directory, then actually `import` the vendored `scripts.doctor` and `scripts.registry.cli` from
that temp copy and call `cmd_doctor`/`cmd_list` against the vendored `_registry_snapshot/` — if
anything the glob missed breaks an import or a read, this fails loudly and directly, not via a
whitelist comparison.

## Explicitly deferred (separate specs)

- `--surface` support for `sb compatibility` (new flag) and real `--surface` behavior for `sb
  doctor` (today vendored as-is from `main`'s existing no-op) — both need
  `compatibility_resolver.resolve(..., surface_kind=...)`, which only exists on the still-open PR
  #256. Small, mechanical fast-follow once #256 merges to `main` and this package's vendored copy
  picks it up naturally — not attempted in this plan.
- `sb install <skill> --host X --scope Y`, `sb uninstall`, `sb verify` — a Python port of
  `install.sh`'s locking (`test_install_concurrency.py`'s stale-lock/reclaim semantics), ownership
  hardening, manifest read/write, and rollback-on-validation-failure behavior
  (`test_install_rollback.py`). Real, substantial port — not attempted here.
- `sb update --channel stable` — no release-channel concept exists in this repo yet; needs its own
  design (channel definitions, how a channel maps to a git tag/release, how `sb` checks/fetches
  updates safely — likely reusing Phase 0/1's version-sync discipline, but that's a future spec's
  job, not this one's).
- A doc/registry validator asserting `docs/skill-framework/shared/host-adapter-contract.md`'s
  capability-family list always equals `host_adapter.CAPABILITIES` (flagged as a recommendation,
  not a finding, by Phase 1's final review) — unrelated to `sb`, a good small follow-up but not
  bundled into this spec to keep scope honest.

## Open questions resolved during brainstorming

1. **Full parity vs. thin wrapper vs. prototype-first?** → Full parity with `doctor.py` +
   `registry/cli.py`'s read-only surface, chosen directly (recommended option accepted).
2. **Distribution mechanism?** → PyPI + pipx (recommended option accepted), not a vendored
   single-file script or bundling `sb` inside every skill install.
3. **Scope for this spec?** → Read-only diagnostics only (recommended option accepted);
   install/uninstall/verify/update deferred to their own specs.
